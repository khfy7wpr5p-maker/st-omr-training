## No repository intake

The repository remains code/contract/test/evidence only. Real score files, user uploads, teacher corrections, permission documents, real MusicXML corpora, private material, datasets, and checkpoints must not be committed.

The Stage 8-1 implementation accepts in-memory `bytes` only. It adds no filesystem writer, upload endpoint, network fetcher, scraper, cloud storage, credential path, or ScoreMosaic connector. Tests use generated MusicXML and synthetic PNG/source-byte fixtures only.

## Quarantine-first rule

`validate_quarantined_sample_bytes(...)` accepts only a `RealDataSample` that still satisfies the Stage 8-0 quarantine contract. A `test` split record is rejected before caller-provided bytes are inspected.

Byte validation alone does not grant training access. The Stage 8-0 admitted development manifest remains the rights/provenance/pairing/leakage authority. A later loader must additionally require the one-to-one Stage 8-1 receipt handoff.

## Source-document byte binding

The source document is format-agnostic at this gate because it may be a PDF, scan, photograph, or other provenance object. It is not used directly as the model input. The gate requires non-empty `bytes`, a 64 MiB maximum, and exact SHA-256 equality with `source_document_sha256`.

This check proves byte identity only. It does not itself prove rights, privacy clearance, musical correctness, or image–MusicXML pairing.

## Training-image contract

The Stage 8-1 training image is restricted to PNG, 8-bit grayscale mode `L`, non-interlaced, single-frame, at most 64 MiB encoded and at most 16,000,000 pixels.

The validator checks the PNG signature, canonical first `IHDR`, `IHDR` CRC, dimensions and encoding fields, then performs full Pillow 12.3.0 verification and decode. The exact image bytes must match `image_sha256`.

Stage 8-1 does not convert arbitrary source formats into this PNG. A future source-to-training-image normalization procedure requires a separate frozen transform/provenance contract.

## MusicXML and semantic identity

MusicXML bytes must match `musicxml_sha256` and pass the existing frozen path used by `tokenize_musicxml(...)`: offline MusicXML 4.0 XSD validation, independent ST-OMR V1 semantic validation, supported-V1 projection, the frozen Stage 7 tokenizer, and tokenizer/detokenizer semantic round trip.

Stage 8-1 defines `semantic_fingerprint` as SHA-256 over canonical JSON containing semantic-fingerprint version `st-real-data-semantic-token-ids-v1`, the exact tokenizer fingerprint, and the exact supported-V1 token-id sequence. The recomputed value must match the Stage 8-0 metadata record.

Automated OMR/OCR/LLM output is still not ground truth merely because it passes structural gates. Stage 8-0 pairing-review evidence remains mandatory for admission.

## Hash-only byte-validation receipt

Successful validation emits `RealDataByteReceipt`. It contains no source, image, MusicXML, permission text, personal data, or model bytes. It binds sample/family/split identity, exact source/image/MusicXML hashes, semantic and tokenizer fingerprints, image dimensions, token count, a perceptual hash, the frozen Stage 8-1 policy fingerprint, and a canonical receipt SHA-256.

The receipt is deterministic integrity/provenance metadata generated by the trusted Stage 8-1 validation path; it is not a digital signature or independent authorization credential. Rights/pairing admission remains a separate Stage 8-0 gate.

## Near-duplicate review

Exact hashes do not detect alternate encodings or minor scan differences. Stage 8-1 adds a deterministic review surface using 64-bit difference hash (`dHash64`) computed from the verified grayscale PNG resized to 9×8 with pinned Pillow LANCZOS. Hamming distance ≤ 4 is flagged as a near-duplicate candidate.

This is a conservative heuristic, not proof of musical identity and not a claim of complete visual-duplicate recall. A candidate under different `family_id` values is a fail-closed development-handoff veto and remains quarantined until family/leakage review is resolved. Same-family candidates remain visible for audit and inherit the Stage 8-0 family-exclusive split rule.

## Development handoff

`validate_stage8_development_handoff(...)` requires a valid Stage 8-0 admitted train/validation manifest, exactly one matching Stage 8-1 receipt per sample, frozen policy/hash/semantic binding, no test records, and no unresolved cross-family perceptual near-duplicate candidate. All Stage 8-0 exact duplicate and family/source/target/semantic leakage vetoes continue to apply.

The development manifest still contains train/validation metadata only plus the opaque `sealed_test_manifest_sha256`. Stage 8-1 does not enumerate, fetch, validate, or inspect real test records.

## ScoreMosaic boundary

ScoreMosaic uploads and teacher corrections remain non-training data by default. User-derived material still requires separate explicit training permission and privacy review. No production request, correction, telemetry event, or inference result triggers model updates. No online/background learning exists, and no Stage 8 output enters ScoreMosaic before Stage 9 quality evidence and the later Stage 10 integration decision.
